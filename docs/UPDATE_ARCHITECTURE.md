# 更新架构与安全边界

## 结论

V1.4.0 采用“检查自动化、安装人工确认”的更新模式：

```text
用户主动检查 / 明确开启打开时检查
→ 请求固定 GitHub Releases API
→ 校验响应大小、JSON、稳定版本号和仓库发布页
→ 对比当前 Manifest 版本
→ 明确显示结果
→ 用户再次确认
→ 只打开 GitHub Release 页面
→ 用户备份、替换本地文件并在 Chrome 中重新加载
```

版本检查不会下载 Release 资产，不会执行远端代码，也不会直接写入扩展目录。

扩展仍只申请 `sidePanel` 与 `storage`，GitHub API 是用户确认后的可选主机权限；Manifest V3 扩展页显式使用 `script-src 'self'; object-src 'none';`。加载已解压模式下没有静默安装、目录覆盖或签名私钥管理能力。

## 为什么不能让加载已解压的扩展静默更新

Chrome 的扩展更新由安装渠道控制：

- Chrome Web Store 安装由 Chrome 按商店机制更新。
- 企业策略管理的浏览器可以使用企业自托管更新。
- “加载已解压”的开发模式不会让扩展覆盖自己的源码目录。

因此本项目不添加对普通用户无效、容易制造错误预期的 `update_url`，也不要求用户把 `.pem` 私钥放进仓库。

## 对旧 douyin-agent 的核对结果

旧项目的关键实现位于：

- `bridge/update_center.py`
- `bridge/http_receiver.py` 的 `/updates/check`、`/updates/apply`、`/updates/rollback`
- `extension/sidepanel.js` 的版本中心交互

该方案依赖常驻本地 Agent。真正自动下载和切换的是经营知识包，而不是浏览器扩展代码。远程知识包必须通过以下检查：

1. HTTPS 来源与最大响应大小
2. 下载文件 SHA-256
3. 固定 Ed25519 公钥签名
4. Schema、更新通道和最低 Agent 版本兼容性
5. 发布时间与失效时间
6. 规则结构校验
7. 临时文件写入、原子替换和有限数量备份
8. 失败时继续使用当前或内置规则包

旧接口也明确拒绝把程序或扩展当成知识包更新，要求它们使用签名安装包。

## 当前项目复用的原则

- **失败关闭：**网络、权限、格式或版本校验失败时，保留当前版本。
- **固定来源：**只访问固定仓库的 GitHub Releases API，并只接受该仓库的 HTTPS 发布页。
- **最小权限：**GitHub API 使用可选主机权限，默认不授权、不联网。
- **不执行远端内容：**响应只解析为有限版本字段，不使用 `eval`、动态模块或远程脚本。
- **用户确认：**检查、开启自动检查、打开下载页、导入备份均由用户明确触发。
- **可回退：**更新前导出工作区并备份源码目录；失败后恢复旧文件并重新加载。
- **状态透明：**区分未检查、检查中、无更新、有更新、权限被拒绝和检查失败。
- **本地数据恢复：**读取时逐键校验；单条损坏记录不会阻止启动，且只在用户列明键并再次确认后清理。
- **页面会话隔离：**独立工作台“开始新一轮”只在二次确认后重置页面内存，不删除 `chrome.storage.local`、侧边栏数据、已发送的 session 收件箱结果或本地文件。

## 当前信任边界

版本检查只能证明 GitHub API 声称哪个 Release 最新，不能代替安装包签名验证。用户在手工下载前仍需确认发布者、版本说明和资产来源。扩展不会把 Release 资产当作可信代码自动执行。

## 如果未来增加本地 updater

若未来需要获得接近旧 douyin-agent 的体验，应单独发布经过签名的本地 updater，而不是让扩展自行覆盖文件。最低要求包括：

1. 安装器与更新器独立签名，私钥只保存在发布环境。
2. 扩展只连接固定的本机地址，并验证一次性授权或本机密钥。
3. 更新清单使用固定公钥验证签名，同时校验包 SHA-256、版本、渠道、大小和兼容性。
4. 解压到临时目录，拒绝路径穿越、额外可执行文件和缺失的 Manifest。
5. 完成静态检查和最小启动健康检查后，再原子切换版本目录。
6. 保留至少一个已验证旧版本；健康检查失败时自动切回。
7. 更新程序不得读取或上传创作任务、报表、素材和浏览器凭据。

在上述本地组件真正实现、签名和发布之前，界面不得声称扩展能够静默自动安装。
